== D. Décisions architecturales

. *Pattern S-082 strict* — 3e runner dédié codex après
  `CodexLicenceCucumberRunner` (S-083) et `CodexOntologyCucumberRunner`
  (S-085). `@SelectClasspathResource` scoped à la feature, glue
  `codex.bdd` partagé (découverte des steps par classe, pas par
  feature), filter tags `@enrichment`. Le `test` task default scanne
  toujours `src/test/resources/features/` via
  `junit-platform.properties` — d'où les variations découverte (+37
  tests dans `test` qui correspondent aux scénarios cucumber ré-exécutés
  par le moteur cucumber-junit-platform quand le `test` task default
  tourne).
. *Background Gherkin* — les 3 inputs (LDD + chunks + graph json) sont
  posés dans le Background pour le scénario 1 (happy path). Les
  scénarios 2 et 3 surchargent `graphFile` après le Background
  (`Given a missing graph json file` / `Given an invalid graph json
  file`) pour exercer le dégradé silencieux de `GraphifyFileResolver`
  sans dupliquer la pose des LDD/chunks. Pattern Cucumber idiomatique.
. *Idempotence prouvée par exécution double* — scénario 4 lance la
  tâche deux fois dans deux outputs distincts (`enriched-1.json` /
  `enriched-2.json`) et compare le contenu texte. C'est la preuve BDD
  que `JsonLddEnricher` est un objet pur déterministe (déjà prouvé en
  unit S-080 `JsonLddEnricherTest.enrich is pure - same input yields
  same output`, ici repris au niveau BDD end-to-end via la tâche
  Gradle).
. *Zéro production modifié* — pure BDD pattern S-085/S-083. Le domaine
  `codex.enrichment` (créé S-080), la tâche `EnrichJsonLddTask` (câblée
  S-086) et le canal Graphify composite (S-087) sont exercés tels
  quels. Aucun fichier `src/main/kotlin/` modifié.
. *Zéro bump BOM* — pas de nouvelle dépendance. `junit-platform-suite`
  déjà présent (S-083). `cucumber.junit-platform-engine` déjà
  `testImplementation` (S-083).
