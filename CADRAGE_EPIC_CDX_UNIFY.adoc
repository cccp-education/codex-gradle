== Audit de l'hypothèse de risque (S-091)

*Résultat de l'audit* : **l'hypothèse de risque S-091 est infirmée**.

`CodexPipelineTask.pipeline()` (lignes 105-137) appelle `chunkMd` à la
ligne 123 mais le résultat n'est utilisé **que pour le log**
(`chunks.size` ligne 128). L'output écrit est `adocContent` (AsciiDoc),
PAS les chunks. Le `mdContent` est aussi éphémère.

.Le chemin pgvector réel (indépendant de `chunkMd`) :
----
ExtractBookStructureTask → ConvertToMarkdownTask → ChunkDocumentTask
                                                      ↓
                                            SemanticChunker.chunk()  ← canonical
                                                      ↓
                                              chunks.json
                                                      ↓
                                          CodexIngestTask → pgvector
----

`chunkMd` ne participe **pas** au chemin pgvector. Les chunks pgvector
sont produits par `ChunkDocumentTask` qui délègue déjà à
`SemanticChunker.chunk()` depuis S-091. L'unification de `chunkMd` ne
peut pas créer de chunks orphelins — `chunkMd` ne produit aucun chunk
persistant.

*Conséquence* : l'unification est un **refactor sécuritaire**. Le
changement observable est limité au log (nombre de chunks peut différer
car `SemanticChunker` gère mieux les sections vides, merge les blanks,
et enrichit avec `overlapNext`/`codeBlocks`/`entities`).

== Décisions architecturales (8)

. *Portée* : refactor pur — remplacer l'appel `chunkMd(mdContent, file.name, license)` par `SemanticChunker.chunk(mdContent, file.name, license)` dans `pipeline()`, supprimer la méthode `chunkMd` (33 lignes).
. *Domaine* : aucun nouveau domaine — modification de `codex.tasks.CodexPipelineTask` existant, `SemanticChunker` déjà en place.
. *Backward compat* : l'output AsciiDoc de `transformCorpusToPdf` est **inchangé** (c'est `adocContent`, pas les chunks). Le seul changement observable est le log (`chunks.size` peut différer — `SemanticChunker` produit possiblement plus de chunks car il gère les sections vides différemment et ajoute overlap/codeBlocks).
. *Pas de fallback* : pas besoin de fallback backward compat — `chunkMd` est éphémère, le contrat de sortie de la tâche est l'AsciiDoc, pas les chunks. Le log n'est pas un contrat.
. *Tests characterization d'abord* : avant le refactor, écrire un test `CodexPipelineChunkingTest` qui exécute `pipeline()` sur un PDF synthétique et verrouille le comportement de sortie (output AsciiDoc non-vide + log contient "chunks"). Ce test doit passer AVANT et APRÈS le refactor (sauf si on assert le nombre exact de chunks, auquel cas on l'assouplit).
. *Cucumber BDD* : feature `codex_pipeline_unified_chunking.feature` 2-3 scénarios `@pipeline @unify` — valide que `transformCorpusToPdf` produit un output AsciiDoc valide + log avec chunks SemanticChunker (pattern CDX-7-4 E2E mais sur PDF synthétique, pas canonique — le PDF canonique est déjà couvert par `CodexPipelineIntegrationTest` S-092).
. *Méthode baby-step TDD strict* : RED (characterization test avant refactor — verrouille comportement output) → GREEN (test passe avec `chunkMd` actuel) → REFACTOR (délégation `SemanticChunker.chunk()` + suppression `chunkMd` — test doit toujours passer). Puis Cucumber BDD RED → GREEN → REFACTOR.
. *Zéro bump BOM* : pas de dépendance modifiée. *Zéro secret*. *Zéro régression* : `./gradlew check` VERT.
